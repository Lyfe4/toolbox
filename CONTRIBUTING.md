# Contributing

## Setup

Node 22 (see [`.nvmrc`](.nvmrc)) and pnpm.

```bash
nvm use
corepack enable pnpm
pnpm install
pnpm dev
```

`src/routeTree.gen.ts` is generated by the TanStack Router plugin and is
committed, so a fresh clone typechecks before it has ever run a build.

[`.env`](.env) is committed too, and holds no secret — just `VITE_SITE_URL`,
the site's own public address, which index.html and `src/app/head.ts` both
need and cannot share any other way. The build fails if it is missing.

Playwright's browsers are only needed for `pnpm check:browsers` and
`pnpm assets:generate`:

```bash
pnpm exec playwright install firefox webkit
```

## The six gates

Everything below must pass. CI runs all six on every pull request, and a
failure is a failure — there is no "warning" tier.

```bash
pnpm typecheck && pnpm lint && pnpm format:check && pnpm test && pnpm build && pnpm bundle:check
```

| Gate                | What it protects                                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm typecheck`    | `tsc -b` across both projects. No `any`, no `!`, no suppressed errors.                                                            |
| `pnpm lint`         | ESLint with `--max-warnings 0`, type-aware rules on. Also bans `eval`, `new Function`, `innerHTML` and `dangerouslySetInnerHTML`. |
| `pnpm format:check` | Prettier. Formatting is not a review topic.                                                                                       |
| `pnpm test`         | Vitest, including axe on every component and route.                                                                               |
| `pnpm build`        | The production build, including the CSP hash and service worker plugins.                                                          |
| `pnpm bundle:check` | The initial JS payload against a 380 kB budget.                                                                                   |

A pre-commit hook runs ESLint and Prettier on staged files. It is a
convenience, not the gate — run the six before opening a pull request.

### Two more that are not in CI

```bash
pnpm build && pnpm check:browsers   # Firefox + WebKit, ~165 MB of binaries
pnpm build && pnpm serve:dist       # the built app under the real _headers
```

`check:browsers` drives the production build in two real engines under the real
CSP. It is out of the CI gate because of the binary download, not because it is
optional — **run it before any change to the canvas, the headers, the service
worker or anything visual.** jsdom has no layout engine, no Worker, no
`OffscreenCanvas` and no pointer events, so the unit suite is structurally
unable to see most of what that script checks.

## Conventions

### Commits

Conventional Commits, present tense, lower case after the type.

```
feat: pipeline execution and shareable graphs
fix: dialog scroll containment and route transition feedback
docs: documentation and deployment
```

Types in use: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`.

The body is for **why**, not what — the diff already says what. If a change
fixes something, say what the actual cause was; if it was surprising, that
sentence is the most valuable thing in the commit.

### Comments

Comments explain decisions, not mechanics. `// increment the counter` is
noise; `// Object.hasOwn, not a bare read: a column literally named "toString"
would otherwise pick up the inherited prototype member` is the reason someone
does not reintroduce the bug in six months.

Where a line is load-bearing for a non-obvious reason, say so in the code. Most
of the sharp edges in this repo are documented at the line that depends on
them.

### Types

- No `any`, no non-null assertions, no `@ts-expect-error` without a comment
  saying what would remove it.
- Prefer making an invalid state unrepresentable over validating it later.
- Import Zod from `@/lib/zod`, never from `zod` — an ESLint rule enforces this.
  The wrapper configures `jitless: true`, because Zod's default code generation
  needs `eval` and the CSP does not allow it.

### Tests

A test should correspond to something that could plausibly break, and its name
should say what. Several of the tests in this repo begin with a comment naming
the bug they exist to prevent; that is the house style.

Property-based tests (`fast-check`) are for anything with a round trip or an
invariant. They have found real bugs here — see the README.

**jsdom has no layout engine.** Anything about geometry, overflow, computed
colour or whether something actually scrolls belongs in
`scripts/cross-browser-check.mjs`, not in a unit test that will silently pass.

## The token layering rule

CSS custom properties are in three layers, and the boundary between them is
enforced by `src/styles/token-layering.test.ts` rather than by convention.

| Layer         | File             | Names     | Who may use it      |
| ------------- | ---------------- | --------- | ------------------- |
| 1. Primitives | `primitives.css` | `--raw-*` | Layer 2 only        |
| 2. Semantic   | `semantic.css`   | `--pb-*`  | **Components**      |
| 3. Themes     | `themes.css`     | `--pb-*`  | Re-declares layer 2 |

**A component stylesheet may only name `--pb-*` tokens, and only ones that
exist.** The test fails the build otherwise.

### Why

Layer 1 is the raw scale — `--raw-amber-500`, `--raw-space-16`. Layer 2 names
_meanings_ — `--pb-accent`, `--pb-border-hairline`, `--pb-surface-raised`.

A component that reaches past layer 2 to `--raw-amber-500` has hard-coded a
decision that belongs to the theme. It will look correct in graphite and wrong
in vellum, and the failure is invisible until someone switches theme — which is
exactly the kind of bug a test should catch and a code review will not.

The rule also means layer 3 has a bounded job: **a theme may only answer
questions layer 2 has already asked.** It re-declares the themed half of the
semantic layer and introduces no new names. That is why adding a theme cannot
break a component, and why `themes.contrast.test.ts` can hold every preset to
WCAG AA by iterating a known list of token pairs.

Adding a token means adding it to layer 2 with a name that describes its role,
and to every theme in layer 3. If you cannot name the role without describing
the colour, it probably belongs in an existing token.

**And to `THEMED_TOKENS` and `TOKEN_GROUPS`**, if it is a colour. Those are what
the theme editor on `/styleguide` offers a user, and a token missing from either
is one nobody can reach. Both are asserted rather than trusted:
`themes.tokens.test.ts` checks the list against the real CSS, and
`customThemes.test.ts` checks that every entry in the list has been grouped and
explained.

A colour token that a user could sensibly be expected to get wrong should also
appear in `CONTRAST_PAIRS` in `features/theme/contrast.ts` — the one list that
both `themes.contrast.test.ts` and the live editor readout iterate. See
[docs/theming.md](docs/theming.md).

## Accessibility

Not a review checklist item — a gate. axe runs against every component and
route in the unit suite, and against every route in two real engines (with
`color-contrast` enabled, which jsdom cannot do) in `check:browsers`.

Two rules that come up repeatedly:

- **Nothing may rely on colour alone.** Port types are shapes. The selected
  palette row is a raised surface _and_ an accent bar. A link inside a run of
  text is underlined, not merely coloured.
- **Styling must not imply behaviour that does not exist.** A `cursor: pointer`
  or a hover state on something with no handler is a defect, and has been found
  in this repo four separate times. Either wire it up or remove the affordance.
